# 前端 5k/50k 规模原型（#52）

**这是丢弃用原型，不在 main 上保留。** 只为回答一个问题：资源库 50000 条时，WebSocket 全量快照 + 前端全量渲染该走哪条路。

## 怎么跑

```bash
.venv/bin/python prototype/ws_scale/measure.py
```

脚本会在本地起一个静态 HTTP 服务，用 Playwright Chromium 打开 `index.html`，对 5,000 / 50,000 条数据分别跑四种 DOM 策略，结果写入 `results.json` 并打印 Markdown 表。

## 四种策略

| 模式 | 做法 | 对应现状 |
|---|---|---|
| `current` | 每次把全部行拼成 HTML，`tbody.innerHTML = ...` | 与 `static/app.js` 的 `renderTable()` 同构 |
| `incremental` | 首屏仍然全量；后续事件只替换命中的那一行 `outerHTML` | 最小改动方案 |
| `virtual` | 全量数据仍在内存；只渲染视口附近约 16 行，上下用 spacer 撑高度 | 虚拟滚动 |
| `page` | 全量数据仍在内存；只渲染 200 条一页，翻页重渲染该页 | 窗口 + 分页 |

所有模式共用同一份 `rowHtml`（6 列、真实长度的名称/URL/状态文案），只改变 DOM 更新策略。绝对毫秒数会随机器变化，方案之间的数量级差异才是结论。

## 测量方法

- Chromium headless，viewport 1440×900，同一台 Mac。
- 首屏：赋值 `innerHTML` 后强制一次布局，再等两帧 RAF（包含样式/布局/绘制）。
- 单事件：更新一条记录，连续 5 次取中位数。
- 跳转：滚到列表中间（虚拟滚动）或翻到中间页（分页），连续 3 次取中位数。
- 每项测量都新建 page，避免前一个模式的热缓存/布局残留。

## 结果（2026-11-12，本机）

| N | mode | 首屏 ms | 单事件中位 ms | 单事件最大 ms | 跳转中位 ms | DOM 行数 |
|---:|---|---:|---:|---:|---:|---:|
| 5,000 | current | 378.2 | 417.2 | 480.5 | 16.7 | 5,000 |
| 5,000 | incremental | 381.1 | 50.5 | 80.4 | 17.1 | 5,000 |
| 5,000 | virtual | 4.3 | 16.6 | 18.7 | 16.8 | 16 |
| 5,000 | page | 17.8 | 16.6 | 16.7 | 18.6 | 200 |
| 50,000 | current | 4105.8 | 4715.6 | 4878.3 | 15.4 | 50,000 |
| 50,000 | incremental | 4124.9 | 584.5 | 776.7 | 16.5 | 50,000 |
| 50,000 | virtual | 4.3 | 16.6 | 17.0 | 16.6 | 16 |
| 50,000 | page | 18.2 | 16.7 | 21.0 | 16.7 | 200 |

## 结论

**选「窗口 + 分页」（每页 200 条），事件只 patch 当前页内命中的行。**

依据：

1. 现状在 5 万条时不可用：首屏 4.1s，每来一条 WS 事件再花 4.7s 全量重建，事件会排队甚至反向拖慢页面。
2. 只做增量 patch 不够：5 千条时能把单事件从 417ms 降到 50ms，但 5 万条时仍有 584ms，且首屏仍是 4.1s。`outerHTML` 替换触发的整表重排是主要成本，不是字符串拼接。
3. 虚拟滚动和分页都能把首屏降到 20ms 内、单事件降到一帧（约 17ms）。分页的迁移面更小：保留现有 `<table>` 语义、行高和勾选逻辑，只增加页码状态与翻页控件；虚拟滚动还要处理滚动位置恢复、动态行高、跳转定位和无障碍语义。
4. 搜索/分类/状态筛选仍走内存里的全量 `Map`，排序也沿用现有 `visibleItems()`，因此筛选行为不变；只是把渲染窗口限制在一页。

**不选虚拟滚动**：除非以后明确要求「连续滚动浏览 5 万条」。那是另一个 UX 需求，不是当前的性能修复。

## 迁移成本与回退

迁移（预计 1 个 PR，只动 `static/`）：

- `static/app.js`：给 `renderTable()` 增加 `page` 状态，按 `PAGE_SIZE=200` 切片渲染；底部加「上一页 / 第 x / y 页 / 下一页」。
- 筛选、搜索、分类切换时把页码重置到 1；删除/新增条目后按总数夹取页码。
- WS 事件：`upsert` 后若该条在当前页，替换那一行；不在当前页只更新内存 `Map`，避免整表重绘。
- 勾选：保留 `selected` Set 的现有语义；跨页勾选仍有效，「全选当前页」需要按当前页处理。
- 不需要改 API、存储或 WS 快照协议；50k 的 `Map` 仍由初始化快照填充。

回退：

- 改动集中在 `renderTable()` 与分页控件，回退一个 commit 即可；也可把 `PAGE_SIZE` 调成 `Infinity` 退回全量渲染（保留代码路径作为临时开关，确认稳定后再删）。
- 不涉及数据迁移，回退不会丢条目/勾选。

## 还没回答的

- 5 万条的快照 JSON 解析和 `Map` 构建本身（在所有方案的共同路径上）没有单独测；如果实测首屏仍被快照拖慢，下一步才是服务端分页/窗口化，而不是继续优化 DOM。
- 移动端窄屏、低端 NAS 浏览器未测；分页在窄屏上比虚拟滚动更容易做无障碍。

## 文件

- `index.html` — 四个策略的可视化原型（可手动切换 N / 模式，页面内打印测量结果）
- `measure.py` — Playwright 自动测量脚本
- `results.json` — 最近一次原始结果

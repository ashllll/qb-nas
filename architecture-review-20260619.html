Problem

UserActionPipeline in services/user_actions.py and PipelineToolTarget in services/agent_tools.py define the identical 5-method protocol. Change one, forget the other — the seam drifts.

Solution

Move the canonical protocol to pipeline.py (next to HarvestPipeline, its sole implementation). Both callers import from one place.

  • locality: protocol change touches one file
  • leverage: one interface, two callers, one implementation
  • interface shrinks from 10 protocol methods (5+5) to 5
  • deletion test: delete either protocol, no callers break — they find the canonical one

C2 — Collapse ToolExecutor into UserActionExecutor

Worth exploring in-process

Before — 7-branch switch + delegate

GET /api/crawl→ToolExecutor.execute("start_crawl")→self._actions.start_crawl()
Agent tool→ToolExecutor.execute("list_items")→store.list()
Agent tool→ToolExecutor.execute("clear_all")→self._actions.clear_items()

interface cost: 7 string-dispatched tool names + dict input/output — read the code to know the contract

After — direct method calls

GET /api/crawl→actions.start_crawl()
Agent tool→actions.list_items()
Agent tool→actions.clear_items()

interface cost: typed method signatures — IDE autocompletes the contract

Problem

ToolExecutor.execute(name, inp) is a 7-branch string dispatcher that mostly delegates to UserActionExecutor. The interface (string name + dict) is nearly as complex as the implementation (a switch). Adding a tool = new branch + new dict key contract.

Solution

Give UserActionExecutor the direct-read methods currently in the switch (list_items, search_items, get_stats). Agent callers call typed methods instead of string dispatch. Remove the switch layer.

Wins

  • depth: interface becomes typed methods, not opaque dispatch
  • locality: tool logic lives in one class, not split across switch + delegate
  • delete 1 shallow module (~80 lines of switch code)
  • deletion test: delete ToolExecutor, complexity concentrates in UserActionExecutor

Risk — Agent tool surface contract

Tool callers currently depend on string names. If external agents reference execute("list_items", ...), collapsing breaks the contract. Verify callers first; if only internal, collapse is safe.

C3 — Centralise the _spawn task-creation pattern

Strong in-process

Before — scattered duplication

pipeline.py:63 def _spawn
user_actions.py:37 def _spawn
qbit_sync.py:48 inline pattern

Same 4-line pattern in 3 modules: if task_manager: create(...) else: asyncio.create_task(...)

After — one canonical helper

bg_tasks.py BGTaskManager.spawn(coro, *, mgr=None)
used by pipeline, user_actions, qbit_sync

Static method that takes optional BackgroundTaskSpawner — one place to evolve the fallback behaviour.

Problem

The "if task_manager: create else: asyncio.create_task" pattern appears in 3 modules. Change the fallback (e.g. add done-callback error logging) and the modules drift apart.

Solution

Add a static BGTaskManager.spawn(coro, *, task_manager=None) method. All three callers use it. The fallback logic lives in one module.

Wins

  • locality: task spawning behaviour changes in one place
  • leverage: N callers get consistent error-logging, lifecycle tracking
  • deletion test: delete the pattern from any module — the canonical one still works
  • natural home for the _on_task_done callback (already added in recent defect fix)

Problem

ItemEventEmitter exists as a separate module, but MagnetItemTransitions is its only adapter. Per "one adapter = hypothetical seam," this is a seam that never materialised. The docstring claims use by QBitSyncLoop — but the code says otherwise.

Solution

Inline the two methods (emit_item_changed, emit_download_result) as private helpers on MagnetItemTransitions. Remove item_events.py. Interface stays identical.

Wins

  • locality: event emission lives next to the state transitions that need them
  • delete 1 file (57 lines) — complexity concentrates where it matters
  • deletion test: delete ItemEventEmitter, 2 methods reappear in transitions.py
  • no change to interface — tests survive untouched

Verify — docstring claims QBitSyncLoop usage

The item_events.py docstring says "Used by both MagnetItemTransitions and QBitSyncLoop." Grep confirms QBitSyncLoop never imports ItemEventEmitter. If a future branch plans to use it, the seam becomes real. Otherwise: inline.

Top recommendation

C3 — Centralise _spawn pattern

Highest leverage per unit of change. Three modules duplicate the same 4-line fallback logic. A 15-line addition to BGTaskManager concentrates task-spawning behaviour in one module, eliminates scattered duplication, and gives the recent _on_task_done error callback a natural home. No interface changes — callers replace self._spawn(coro) with BGTaskManager.spawn(coro, task_manager=self._task_manager).
